RFC is in `document.md`. Highlights on what I did with your framing, since I didn't just transcribe it:

**Pushback on the framing.** "It's between API Gateway or Redis-on-K8s" is a hypothesis about the option space, not the option space. I kept both as candidates but added two more: rate limiting at the Kubernetes ingress/service-mesh level (config only, no new app code, no new AWS component — the credible option neither of your two named), and a plain "do nothing" baseline for comparison. I also flagged "buy a dedicated API-management platform" (Kong/Apigee/Cloudflare) and set it aside in one paragraph — it's overkill for what's actually required here.

**The recommendation:** AWS API Gateway native throttling (REST API + usage plans/API keys), with an AWS WAF rate-based rule shipped in parallel as an immediate stopgap while the API Gateway migration is in flight, since every day unprotected is continued exposure to the abuse pattern that already happened. Redis-backed middleware is explicitly rejected — nothing in the derived requirements needs limiting logic richer than "two tiers, per identity," which usage plans already give you, and building it would add a new stateful, hot-path dependency the team doesn't need to own for this. The one condition that flips the call: if you already know you'll need cost-aware limits (e.g., expensive queries cost more quota) or a quota shared across multiple public APIs, build the custom layer from the start instead — retrofitting it later means running two enforcement points at once. That's the strongest objection to my own pick, spelled out in the decision section.

**What I could not verify, and treated as assumed (flagged inline, not silently asserted):** I had no access to your dashboards, incident tickets, cloud console, or the `public-search-api` code, so four things that materially affect the tradeoff are stated as assumptions rather than facts — pull these before the meeting, they're each roughly 5 minutes of lookup:
1. Whether `public-search-api` already sits behind any AWS edge (ALB/CloudFront/API Gateway) — this changes whether the WAF stopgap ships in hours or needs its own setup first, and whether "adopt API Gateway" is a small change or a real migration.
2. Real traffic and abuse figures (peak rps, single-source vs. distributed) — without these I could not size any threshold; the RFC's non-functional targets are placeholders pending this.
3. Whether the team already runs Redis in production anywhere — if so, Option B's operational cost is much lower than I modelled, and worth reopening.
4. Whether any callers already use an API key, or everything is anonymous today — affects how much of the tiering requirement is free.
